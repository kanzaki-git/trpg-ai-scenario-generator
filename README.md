# 1. サービス概要

TRPG配信やリプレイ動画を見て興味を持ったものの、ルール理解やシナリオ準備の負担によって始められていない人向けのWebサービスです。

ユーザーはジャンル、世界観、プレイ人数、プレイ時間などを入力するだけで、AIがセッションで利用できるシナリオの土台を生成します。

生成される内容には、導入、登場人物（NPC）、発見できる手がかり、イベント、真相、エンディング候補が含まれています。

AIはシナリオの土台を作成し、ゲームマスター（GM）は内容の確認や必要に応じた調整、参加者の行動に応じた状況説明や進行を担当します。

プレイヤーはそのシナリオをもとに行動や選択を行い、GMの進行によって物語を楽しみます。

物語をみんなで作り上げる楽しさはそのままに、ルールブックの購入やシナリオ探し、GMの準備負担を減らし、「遊びたい」と思ったその日に友人と遊び始められる環境を提供します。

# 2. このアイデアはどこから生まれたか

## 2-1. きっかけとなった体験・感情

私はTRPGの配信やリプレイ動画を見ることが好きで、自分でも友人と遊んでみたいと思っていました。

しかし実際に始めようとすると、ルールブックの購入やルール理解、自分たちに合ったシナリオ探し、ゲームマスターによる事前準備など、多くの工程が必要でした。

その結果、「面白そうなのに始めるまでが大変」と感じ、結局遊ぶまでに至らなかったことがあります。

私が魅力を感じていたのは、細かなルールやシステムではなく、友人と一緒に物語を作りながら遊ぶ体験そのものでした。

そこで、その楽しさだけをもっと手軽に体験できる仕組みがあれば、多くの人が気軽に遊び始められるのではないかと考え、このサービスを思いつきました。

## 2-2. なぜそれが気になったのか

私はゲームや娯楽を楽しむ際に、できるだけ手軽に始められることを重視しています。

また、面白そうなコンテンツであっても、始める前の準備や学習コストが高いと、興味を持った人が途中で諦めてしまう場面を何度も見てきました。

物語を作りながら遊ぶ体験には大きな魅力があります。

しかし、その魅力に触れる前の準備段階で離脱してしまう人も少なくありません。

私は「やってみたい」と思った人が、その気持ちのまま遊び始められる環境を作りたいと考えています。

## 4-2. 自分とユーザーの距離

過去の自分です。

私自身がTRPG配信を見て興味を持ちながらも、ルール理解やシナリオ探し、準備の負担によって実際に遊ぶまで至らなかった経験があります。

## 4-3. 実際に使われる可能性について

最初に利用してくれるのは、物語を作りながら遊ぶ体験に興味を持ったものの、準備の多さによってまだ遊べていない人だと考えています。

本サービスは物語生成そのものではなく、「すぐに遊び始められる状態を作ること」に価値があります。

## 4-4. ユーザーがサービスを導入して利用するまでのイメージ

1. ユーザーがジャンル、世界観、人数、プレイ時間を入力する

2. AIがシナリオの土台を生成する

生成内容

・導入
・登場人物（NPC）
・手がかり
・イベント
・真相
・エンディング候補

3. GMが内容を確認し、必要に応じて調整する

4. プレイヤーは行動や選択を行う

5. GMは参加者の行動に応じて状況説明やNPCの演技、進行を担当する

6. プレイヤーの選択によって新たな情報やイベントが発生する

7. 真相へたどり着き、行動や選択の結果に応じたエンディングを迎える

ユーザーはルールブックや既存シナリオを用意することなく、短時間で遊び始めることができます。

# 5. 既存サービス・競合調査

## 5-1. 似たサービスの調査

| サービス | できること | 課題 | 本サービスとの違い |
|-----------|-----------|-----------|-----------|
| ChatGPT | シナリオや設定を生成できる | 指示の出し方が難しい | 遊ぶことを前提とした形式で出力する |
| Claude | 長文の物語を生成できる | 情報量が多く整理が必要 | 物語進行に必要な情報のみを出力する |
| BOOTH | TRPGシナリオを購入できる | シナリオ選びに時間がかかる | 条件入力だけでシナリオを生成できる |
| TALTO | TRPGシナリオを検索できる | 自分に合うシナリオを探す必要がある | シナリオ探しそのものを不要にする |
| AI Dungeon | AIと対話しながら物語を進める | 自由度が高く初心者は迷いやすい | 友人同士で遊ぶことを前提としている |

## 5-2. それでも自分が作りたい理由

私はシナリオ生成サービスを作りたいのではありません。

「遊ぶまでの負担」を減らし、物語体験を始める最初の一歩を後押しするサービスを作りたいと考えています。

## 5-3. 差別化を体験価値で表現する

既存サービスが物語生成そのものやシナリオ販売を提供するのに対し、本サービスは「物語を作りながら遊ぶ体験を手軽に始められること」に価値を置いています。

ユーザーはシナリオを探したり、長いルールブックを読んだりすることなく、AIが用意したシナリオをもとにその日のうちに遊び始めることができます。

私はシナリオ生成サービスを作りたいのではなく、物語体験を始めるまでのハードルを下げるサービスを作りたいと考えています。

# 8. このアプリの懸念点とその対策

## 懸念点①

生成されたシナリオが実際には遊びにくい可能性がある。

対策

・テストプレイ実施
・フィードバック収集
・プロンプト改善

## 懸念点②

既存生成AIとの差別化が難しい可能性がある。

対策

・初心者向け入力フォーム
・GM向け構造化出力
・遊ぶための準備支援に特化

## 懸念点③

著作権に関する問題が発生する可能性がある。

対策

・特定作品の再現を目的とした利用を想定しない
・オリジナル設定を生成するプロンプト設計
・利用規約で生成物の取り扱いを明記
・既存作品の再現利用を推奨しない

## 10-2. 技術選定の比較検討

| 候補 | 採用 / 不採用 | 理由 |
|--------|--------|--------|
| Ruby on Rails | 採用 | RUNTEQで学習しており、短期間でMVPを開発しやすいため |
| Laravel | 不採用 | PHPの学習コストが発生するため |
| Django | 不採用 | Python経験が少なく、開発期間内での習得が難しいため |
| PostgreSQL | 採用 | Renderとの相性が良く、本番環境でも利用しやすいため |
| MySQL | 不採用 | PostgreSQLを優先して利用するため |
| Render | 採用 | 無料枠があり、Railsアプリを素早く公開できるため |
| AWS | 将来的に採用検討 | 本リリース後にインフラ構築経験を深めるため導入を検討 |

## 10-3. キャッチアップ不足の懸念

OpenAI APIを利用した開発経験がないため、学習コストが発生する可能性があります。

そのためMVPでは

・シナリオ生成
・シナリオ保存
・シナリオ閲覧

に絞り、

「準備の負担なく物語体験を始められるか」

という価値の検証を優先します。
